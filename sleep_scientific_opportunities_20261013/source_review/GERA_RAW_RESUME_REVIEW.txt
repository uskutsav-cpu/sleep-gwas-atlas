Actual code correctness review
The added resume mode retains the original acquisition helper and uses fixed /usr/bin/curl with --disable first, HTTPS only, quoted If-Match, identity encoding, exact finite Range, CONNECT-header suppression and no retry/redirect/TLS-bypass flags. Complete final response headers must be 206 with the exact single ETag, Content-Range and Content-Length. Missing, contradictory/duplicate, weak or wrong validators and nonidentity Content-Encoding are rejected. Informational header blocks do not serve as successful final evidence. Invalid response headers reject continuation before assembly; actual suffix size must equal the remaining length.

The prefix is opened read-only. Suffix and candidate are exclusively created in a new owned staging directory. The helper verifies prefix SHA before requesting bytes, hashes the copied prefix against the frozen identity, streams full MD5/SHA while assembling, checks complete file length and the known published full MD5, fsyncs, confirms plan immutability and only then attempts nonclobbering publication. Range metadata alone cannot promote a source. An existing destination stays untouched; if publication does not complete, the candidate remains and the operation fails rather than claiming success.

One concrete defect was discovered and corrected before admission: a malformed complete HTTP status line could raise IndexError before the failure receipt was written. The reviewed helper guards status tokens and treats the malformed block as invalid, retaining the failure-receipt path. No source or scientific protocol changed for this repair.

Actual focused tests
Thirty independent synthetic checks passed against the reviewed helper: 18 header cases and 12 local resume_main cases. These directly exercised the actual code with synthetic 64-byte data and an intercepted curl launch, not a mirror implementation. Header cases included wrong200, offset, end, total, version/case/weakETag, Content-Length, gzip, duplicate validators, incomplete and malformed headers, informational and multiple final blocks. Local cases covered correct assembly/publication, wrong200/offset/version, truncated suffix, full-checksum failure, changed plan, staging cap, wrong pre-request prefix, existing destination and a publication race. Actual BSD mv-n behavior was exercised; all rejected cases retained their prefix and never promoted an unverified source. The malformed-header case produced a preserved failure receipt. No real remote/source data were used in these tests.

Resource and checkpoint bounds

The 128 MiB observed curlRSS limit, 1 GiB internal emergency floor, 8 GiB initial SSD free-space requirement and 5.5 GB aggregate owned staging cap are retained in the new plan; the separate native 3 GiB guard is unchanged. The wider time bound is justified by the observed transfer rate, but neither these tests nor the plan guarantee that the server will complete within it.

Any real result must still satisfy exact response/length/checksum gates and preserve transport and attempt receipts. A failure keeps the prefix and owned recovery artifacts and stops; it does not authorize silent full redownload, automatic retry, an incomplete-source analysis or statistical fallback. Full published-MD5 verification admits complete artifact identity only; downstream scientific/QC admission remains separate.
